# GrogLog

A drink tracker for iOS (SwiftUI, GRDB, in `GrogLog/`) and Android (Compose, Room, in `android/`). The README holds the
decisions worth knowing, so read it before changing how days, units, prices or sync work. The apps share a Rust core in
`core/` (days, units and, as it moves across, the rest of the logic) and a backup format; presentation and storage stay
native.

## Git

- Work in PRs; never push to main. PRs are squashed; merge main into a branch rather than rebasing.
- Never push tags. CI tags and publishes the GitHub release when a release PR merges.
- Commits are signed.

## Changelog

`CHANGELOG.md` is generated by `scripts/changelog.py` and never edited by hand. Every change adds one fragment under
`changelog.d/unreleased/<section>/`, named `<yyyymmdd>-<slug>.md` and holding one `- **Lead.** Detail.` entry; to
correct a note, edit its fragment. `just changelog --stdout` previews the result. The format is in
`changelog.d/README.md`.

## Releasing

`just release patch|minor|major` (or an exact `X.Y.Z`) branches from main, raises `MARKETING_VERSION` in `project.yml`,
the one place the version lives for both apps, turns the unreleased fragments into the version and opens the release
PR; `gh workflow run release.yml` does the same from CI. Merging it is the release: the Android workflow publishes the
GitHub release with the signed APK and the changelog section as notes. A push releases only when `MARKETING_VERSION` is
newer than the latest GitHub release, so a release that failed is made by the next push that runs the Android workflow.
TestFlight and Play's internal track receive every push to main, release or not; App Store submission and Play
promotion stay manual (see `docs/releasing.md`).

## Docs

A change to behaviour, a setting or the backup format updates the matching page in `docs/` in the same PR.
`docs/IMPORT.md` is the contract between the apps' backups, so a change there changes both.

## Build and check

```sh
scripts/core-apple.sh   # build the Rust core for iOS; run before xcodegen
xcodegen generate       # GrogLog.xcodeproj is generated, never committed
scripts/ci-test.sh      # the iOS tests, on whichever iPhone simulator exists
just phone              # build, install and launch on the connected iPhone
just android-test       # the Android JVM tests
just android-build      # debug APK
just android-install    # install on a running emulator or device
just changelog --stdout # preview the assembled changelog
just release minor      # open the release PR
just store              # App Store Connect, from the terminal
just play               # Google Play, from the terminal
```

The Android recipes use `ANDROID_HOME` from the environment when it is set, so unset it if it points at a directory that
does not exist; otherwise they use Homebrew's SDK.

## Where things live

- `core`: the shared Rust crate, exposed to Swift and Kotlin through uniffi. `core/out` is generated and not committed.
- `GrogLog/Model`: the database, `Logbook` (every write goes through it), `Ledger` (derived totals), goals, units and the
  catalogue. `GrogLog/Views` has a folder per tab; `GrogLog/Sync` is CloudKit; `GrogLogWidgets` the widgets.
- `android/app/src/main/java/cc/blit/groglog`: `model`, `data`, `export`, `ui` (a package per tab), `widget`, `shortcut`.
- The catalogue's table is `core/src/catalog_data.rs`, and its lookups and the exchange rates are in `core/src/catalog.rs`
  and `rates.rs`. Both apps read them through the core; `Catalog.swift` and `Catalog.kt` only map its records onto their
  own types. A brand's name and kind are the identity logged drinks refer to, so renaming one is a data change.

## Copy

In-app text is formal but warm: no contractions, no em dashes. Medical and settings text states what a thing does and
why, without cleverness.
